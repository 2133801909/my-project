# 文档维护规范

## 原则

- 文档是接口合同，不是营销材料。
- 代码变更导致文档过期时，**同一次提交内**修复文档。
- 历史决策只追加，不改写；被取代时在旧 ADR 顶部标注“已被 ADR-XXXX 取代”。

## 何时必须更新

| 变更                       | 必须更新                                               |
| -------------------------- | ------------------------------------------------------ |
| 新增/修改导出函数签名      | `docs/modules/domain.md` 或对应模块文档                |
| 新增 reducer action / 字段 | `docs/modules/state.md`、`architecture/state-model.md` |
| 新增路由/页面              | `architecture/routing.md`、`modules/features.md`       |
| 存储键/迁移/配额策略       | `architecture/data-flow.md`、ADR 0003                  |
| 技术栈/构建/测试框架       | 新 ADR + `AGENTS.md` 命令区                            |
| 演示边界                   | `conventions/demo-boundaries.md` + 新 ADR              |
| 新增目录                   | `docs/README.md` 索引 + 新模块文档                     |

## 文档结构

- 每篇开头一句话说明范围。
- 接口用代码块给出真实签名；不要写伪代码。
- 规则用列表/表格；避免长段落。
- 交叉链接使用相对路径。
- 中文为主；代码、路径、命令保持原文。

## 评审清单

- 文档中的路径、函数名、命令是否真实存在？
- 是否把“计划”写成“已实现”？
- 是否与 `AGENTS.md` 的导航矛盾？
- 是否泄露真实用户数据/密钥？本项目不应包含任何密钥。

## 给 AI 的提示

`AGENTS.md` 是入口；详细规则在 `docs/`。若文档与代码冲突：

1. 以可运行代码与测试为事实来源；
2. 在同一次修改中修正文档；
3. 若冲突涉及产品边界，先停下并询问用户，不要自行放宽边界。
